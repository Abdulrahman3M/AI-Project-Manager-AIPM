# AI Project Manager Agent Rules

- Work only inside this repository unless the owner explicitly authorizes another path.
- **AIPM Self-Protection (Mandatory):** When AIPM is being used to manage or assist another project, treat this repository's entire root as a protected product installation. Do not create, edit, delete, move, rename, format, regenerate, or clean any file or folder under it, and do not point managed-project state or the project registry into or across this root. Only a direct, explicit user request to develop or repair AIPM itself authorizes source changes here; ordinary AIPM use, broad autonomy instructions, or work on another project do not.
- The Core Engine independently enforces the same boundary for managed-project roots, project-state operations, and registry files/backups: any path equal to, inside, or containing the detected AIPM installation is rejected before the operation. The Core guard is fail-closed and has no user-facing bypass for ordinary project workflows.
- This rule and Core guard do not replace operating-system or AI-host permissions: an external agent with direct filesystem write access can bypass application APIs. Keep AIPM outside that agent's writable workspace, or deny writes through the host sandbox/ACL; use a separately authorized AIPM-development session when changing AIPM.
- The owner may add or remove Skills in `01-Skills-General`. Keep provenance and license metadata accurate; preserve source hashes for retained imported Skills. Declare new AIPM-authored Skills in `Capability-Library/First-Party-Skills.json`; update protected capability baselines only through the confirmed CLI workflow.
- `project-orchestrator` is the documented derivative; `browser-environment-manager`, `powershell-tui-app-designer`, and `tui-intelligence` are the declared AIPM first-party Skills in `Capability-Library/First-Party-Skills.json`. The PowerShell TUI App Designer retains its original migration source hashes as provenance while being maintained under owner authorization.
- Do not add `02-Skills-Personal`, `import-memory`, or `morning`.
- Use English Title Case for new human-facing names. Preserve technical filenames and Skill slugs.
- Do not push, publish, or modify the Universal AI ToolKit source without explicit authorization.
- Apply the AI Project Manager Personal Use License to project material and generated distributions.
- Treat `Capability-Library/Registry.json` and its provenance ledger as protected integrity baselines. Refresh only with the explicit CLI confirmation flag, a reason, and required version/changelog updates.
- Generate the legacy Project Agent Bridge only with `Maintenance-Tools/Invoke-Capability-Library.py`; generate multi-host distribution archives only with `Plugins/Build-System/Build-AIPM-Plugin.ps1`. Keep all output inside this repository and unpublished/uninstalled unless separately authorized.
- **Automatic Plugin Synchronization:** Any addition, removal, reorganization, or functional, technical, instructional, or supporting-file change to a Skill or Prompt requires a Plugin impact review before the task can be complete. Identify every affected legacy and multi-host distribution; update required version, metadata, and changelog records; rebuild ChatGPT/Codex, Claude Code, and Google Antigravity archives with the approved build commands; validate their inventories, hashes, exclusions, and host-specific manifests; and report the updated package names, versions, paths, and target platforms. A package is never considered installed merely because it is ready for the host's documented installation/update mechanism.
- **General Skills Documentation Synchronization:** Any addition, edit, rename, functional or usage change, move, or removal of a Skill in `01-Skills-General/` must update `docs/guides/General-Skills.md` in the same task. Keep one entry for every actual Skill master, remove entries for deleted Skills, and update its display name, description, usage guidance, and source link whenever the source changes. Do not mark a task that changes General Skills complete until this index matches the live files.
- **General Prompts Documentation Synchronization:** Any addition, edit, rename, functional or usage change, move, or removal of a standalone Prompt in `02-Prompt-General/` must update `docs/guides/General-Prompts.md` in the same task. Keep one entry for every actual standalone Prompt and none for removed files; Skill-owned Prompts remain with their owning Skills and are not duplicated in this index. Do not mark a task that changes General Prompts complete until this index matches the live files.
- **Capability Index Quality Rules:** Keep both indexes in alphabetical order by displayed name, use English Title Case, and preserve each technical Skill slug or original Prompt filename exactly in inline code. Check every source link after a move or rename, remove deleted items, add new items, and revise descriptions and usage guidance when a capability's purpose changes. Verify inventory counts, duplicates, ordering, source links, README links, and return-to-home links with `python -m unittest discover -s Tests -p "test_general_capability_docs.py" -v`.
- **SemVer Change Scope:** For every change, identify the smallest versioned component(s) whose behavior, content, or shipped artifacts changed, and increment only those versions according to SemVer and the component's changelog/release process. Propagate the version change to dependent distributions and aggregate products only when their shipped content, compatibility, metadata, or release records are affected; do not bump unrelated components for a subordinate-only change. For example, a Skill change updates that Skill's version and changelog, every affected Plugin/distribution version and metadata, and the overall project/platform version only when the project release includes or records that change. Changes to the AIPM product source update the platform/project version and the TUI version together, with both changelogs and versioned release notes. Apply the same scope-based rule to other independently versioned components.
- Keep host adapters capability-declared, permission-gated, and fail-closed. A package-format manifest does not mean installed or runtime-tested; never infer local file access for ChatGPT text conversations.
- **Core Architectural Principle — Task Context, Not Project Implementation:** AIPM manages project registration, task metadata, task-scoped supporting artifacts, progress notes, evidence, and handoffs under the managed project's `Shared-Project-State-Manager/`. AI Agents perform implementation, documentation edits, and project-specific tests directly in the target project's original files, subject to that project's rules and the host/OS permissions already in force. Core must not expose project-source edit, delete, overwrite, or execution APIs, copy implementation files into task folders as working duplicates, execute the target project's tests, or impose an AIPM approval gate on agent changes. Task metadata/artifact write controls protect only AIPM-owned state; they neither authorize nor approve project-source changes. Record changed source paths and agent-reported evidence as references, not as copies or claims that AIPM performed the work.
- Maintain independent tasks under `Shared-Project-State-Manager/Tasks/<Task-ID>/`. The Core manifest is authoritative for status and checkpoint fields; generated task-state, plan, test-status, and handoff documents are readable projections. Keep task instructions, handoffs, reports, helper scripts, examples, and references in their declared task categories. Import only task-supporting material that the next agent needs; the working implementation remains in the original project tree. A new agent must re-read current project files and verify the checkpoint against live project evidence before resuming.
- Treat `UX-TUI/Visual-References/` images as design references only. Do not claim a working or no-flicker terminal UI until real host/version tests are run.
- For every AIPM product release, increment the platform and TUI versions together using SemVer; update both changelogs and add versioned release notes. Follow **SemVer Change Scope** to decide whether a change warrants that product release.
- Keep the root README product title, adjacent version, release/status badges, and latest-release link synchronized with the current release. Update the Support Matrix and release index as needed, then build and verify the source ZIP and SHA-256 sidecar before publishing.
- Publish the same verified source ZIP and checksum sidecar attached to the matching `vX.Y.Z` GitHub Release; verify the remote tag, assets, and checksum against the local build. Do not claim CI, host, or cross-agent checks that were not run; avoid paid Actions when not authorized or available.
- Preserve independently versioned Skills and Plugins unless their own content or metadata changes require a version update; when they do, follow **SemVer Change Scope** and the Plugin synchronization requirements above.
